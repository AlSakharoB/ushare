# Распознавание чеков: модели и измерения

## Этап A. Базовый выбор модели

Основной локальный стек: **PaddleOCR 3.x**, детектор **PP-OCRv5_server_det**, распознаватель **cyrillic_PP-OCRv5_mobile_rec** для русских чеков, document orientation + опциональный **UVDoc** для искривлений; OpenCV для crop/перспективы. Для английского отдельный поддерживаемый English recognizer при необходимости.

Это выбранная отправная конфигурация, а не обещание лучшей точности на любых чеках. У текущей документации есть более новые семейства; не подменяй кириллический recognizer стандартной китайско-английской моделью и не считай совместимость автоматической. На S09 проверь наличие точных артефактов, совместимость PaddleOCR/PaddlePaddle и pin модели по revision/checksum. Если более новый PP-OCRv6 имеет документированную поддержку нужного языка, сравни его тем же benchmark и выбирай по результатам. Использование проверенного v5 допустимо.

Резервный кандидат для сложных случаев: **Qwen/Qwen3-VL-8B-Instruct**, отдельный локальный endpoint. Не включать его в обязательный CPU-профиль: требования VRAM/RAM и latency измерить. Официальное описание заявляет OCR и работу с наклоном/размытием, но превосходство на наших чеках надо доказать. Не навязывать платный внешний API. Наличие Codex не означает, что пользователю доступен production OCR API.

Интерфейс `ReceiptRecognitionProvider` позволяет benchmark нескольких моделей без переписывания UI/домена. PaddleOCR baseline обязателен; Qwen сравнить при наличии вычислительных ресурсов, иначе явно отметить `NOT_RUN`, не симулировать его качество моками.

## Этап B. Pipeline

1. Принять изображение, проверить формат/лимиты, нормализовать EXIF orientation и цвет, сохранить private original.
2. Показать preview. Дать создателю crop по 4 углам и поворот 90°. Автоматический crop — предложение, не безусловное обрезание сумм.
3. Оценить blur, glare, низкий контраст, обрезанные края. При плохом фото предложить переснять; manual остаётся доступен.
4. Определить ориентацию, выправить перспективу. UVDoc применять для деформаций как отдельный профиль. Не применять одновременно несколько усилений, ухудшающих цифры, без benchmark.
5. Выполнить OCR с polygons/bboxes и confidence строк. Длинные чеки обрабатывать с overlap/tiles и дедупликацией по координатам; одинаковые товары в разных строках не сливать.
6. Сгруппировать строки геометрически, выделить названия, quantity, unit_price, line_total, скидку, печатный итог. Отличать товар от ИНН, НДС, времени, номера фискального документа и «получено/сдача».
7. Нормализовать десятичную запятую, пробелы и `₽`; uncertain `O/0`, `З/3`, `Б/6` не заменять по всему тексту слепо. Каждое исправление имеет reason и исходный фрагмент.
8. Проверить арифметику и полноту. Неразборчивые поля = null и warning, а не догадка.
9. Вернуть кандидаты по schema и привязку к crop исходного фото. Обязательно редактирование создателем перед применением.
10. Применить выбранные кандидаты атомарно по expected_version. По умолчанию «добавить», режим «заменить» явно предупреждает об удалении строк/долей и разрешён только в допустимом статусе. Повтор apply по одному job/key не дублирует позиции.

OCR никогда не открывает распределение, не подтверждает оплату и не закрывает чек. Повтор распознавания не перезаписывает ручные исправления автоматически.

## Этап C. Schema кандидатов

```json
{
  "currency": "RUB",
  "merchant": null,
  "printed_total_minor": null,
  "detected_discount_minor": null,
  "items": [{
    "name": "Пицца",
    "quantity": "2",
    "unit_price_minor": 80000,
    "line_total_minor": 160000,
    "asset_index": 0,
    "source_bbox": [10, 20, 800, 90],
    "evidence_text": "Пицца 2 x 800,00 1600,00",
    "ocr_confidence": 0.87,
    "warnings": []
  }],
  "warnings": [],
  "provider": "paddleocr",
  "model_revision": "PINNED_AT_IMPLEMENTATION"
}
```

Для null нужны nullable types. Confidence PaddleOCR не является вероятностью правильной суммы; отдельно считай score/warnings арифметики. Не создавать фальшивые точные confidence для VLM: null и `needs_review`. OCR-discount — кандидат; создатель выбирает, уже включён ли он в строках, чтобы не применить дважды. Для multi-image хранить bbox каждого source и не объединять совпавшие позиции без подтверждения.

## Этап D. Реальный benchmark

Минимум 30 разных обезличенных реальных чеков: 10 нормальных, 10 наклонённых/мятых/длинных, 10 с плохим светом/размытием. Разнести train/dev/holdout по исходному чеку, а не по его разным crop. Все синтетические варианты одного чека остаются в той же группе. При нехватке реальных чеков synthetic пригоден для plumbing, но не доказывает качество OCR. Запроси недостающие фото один раз и продолжай другие этапы; OCR quality gate остаётся `BLOCKED`, пока реальный набор не собран.

Ground truth: реальные строки, поля, суммы, скидки, итог, quality tags, readable/illegible. Два прохода ручной сверки числовых полей; неизвестное не размечать догадкой. Приватные фото/тексты не коммитить без разрешения; для git — обезличенные разрешённые fixtures, hashes и безопасные агрегаты. Если артефакты приватные, хранить путь и checksum в gitignored manifest.

Метрики: item detection precision/recall/F1; exact match line_total; exact match quantity; exact printed total; CER названий; доля полностью верных чеков; missed/extra rows; unsafe-high-confidence errors; p50/p95 latency, peak RAM/VRAM, timeout rate. Считать accuracy сумм по всем читаемым ground-truth строкам; пропуски = ошибки. Матчинг строк один-к-одному, объяснить алгоритм и пороги до holdout. Missing total — ошибка в знаменателе, если он виден в оригинале.

Сравнить как минимум Paddle без preprocessing и с preprocessing/UVDoc. Qwen — если доступен. Сохрани сырые обезличенные результаты и отчёт с CPU/GPU, revision, параметрами, числом изображений в каждой группе. Не выбирать профиль только по среднему CER: цена важнее названия.

### Целевые ворота качества, а не заявленная точность

- Normal: ≥98% exact line_total, ≥95% item recall, ≥98% exact total среди читаемых чеков.
- Difficult readable: ≥90% exact line_total, ≥90% item recall; ≥95% exact printed total.
- Severe: лучше безопасный `needs_review`/reshoot, чем выдуманные строки; отдельно показать все ошибки сумм.
- p95 ≤20 секунд на одном изображении в выбранном production-профиле; измерять end-to-end и отдельно inference. Иначе честно пометить performance gate failed и предложить настройки/ресурсы.
- Проверка человеком обязательна даже при достижении целей. Малый holdout даёт ограниченную оценку; опубликовать counts, не только проценты.

Если целей нет: диагностировать ошибки, улучшить preprocessing/parser/модель и повторить честно. Не понижать пороги незаметно, не объявлять этап готовым потому что «модель скачалась». Дополнительные модели и облачные расходы не подключать молча.

## Этап E. Отказоустойчивость

Модель отсутствует, OOM, timeout, плохое фото, provider недоступен, невалидабельный JSON → job failed/needs_review, безопасное сообщение и manual fallback. retries только для transient errors, max attempts, отсутствие параллельных дублей. Поздний результат после закрытия/удаления не применяется. Rate limit и очередь ограничены. Model download — build/setup задача с checksum; runtime не должен неожиданно качать гигабайты при первом запросе.
