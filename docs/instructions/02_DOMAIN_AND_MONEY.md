# Домен, деньги и состояния

## Этап A. Зафиксировать состояния

| Статус | Возможности | Переход |
| --- | --- | --- |
| `draft` | Создатель меняет чек, проверяет OCR, приглашает; участникам доступен только экран приглашения | Создатель → `collecting` |
| `collecting` | Принятые участники читают чек и меняют свои доли; создатель редактирует позиции | Создатель → `settling`, если выполнены условия |
| `settling` | Доли и параметры заморожены; идут отметки переводов и подтверждения получения | Создатель → `closed` либо явно обратно в `collecting` |
| `closed` | Только чтение для участников до `purge_at` | Очистка через 7 суток |

OCR job имеет собственный статус, не является статусом чека. Нет автоматического закрытия после кнопки участника «Перевёл». Нет обычного API полного удаления открытого чека в MVP.

## Этап B. Определить денежные поля

- Все суммы — целые minor units: 12345 = 123,45 ₽. Python `int`/SQL `BIGINT`, JSON integer. Ограничить допустимые значения безопасным диапазоном JS Number; по умолчанию общий чек ≤100 000 000 minor units.
- Для дробного количества и процента использовать Decimal из строки, не binary float.
- `share_bp` целое 0…10000: 1 bp = 0,01%; 10000 = 100%. Общая сумма bp строки ≤10000.
- `line_total_minor` — авторитетная стоимость строки до общей дополнительной скидки. `quantity`, `unit_price_minor` — дополнительные поля; если они расходятся с итогом, создатель должен подтвердить/исправить причину. Строчный итог уже может учитывать скидку магазина на эту строку.
- Позиция имеет ненулевую положительную стоимость; нельзя создавать отрицательные товары ради подгонки итога. Скидка отдельная.
- Скидка `D`: либо фиксированная 0…S, либо `round_half_up(S × discount_bp / 10000)`.
- `S = sum(line_total_minor)`; итог после скидки `N = S − D`.
- Чаевые `T`: либо неотрицательная фиксированная сумма, либо `round_half_up(N × tips_bp / 10000)`. Для чаевых процент допускается 0…10000 bp в MVP. Итог `G = N + T`.
- Сканированный напечатанный итог — контрольное поле, а не сумма, принудительно заменяющая товары. Разницу показывать и разрешать явное подтверждение создателем с причиной; ничего не выдумывать.

## Этап C. Алгоритм без потерянных копеек

Используй метод наибольших остатков с точной рациональной арифметикой. Для распределяемого целого `A` и весов `w_i`: посчитать точные `A*w_i/sum(w)`, взять floor, остаток раздать по убыванию дробной части. При равенстве — стабильный UUID участника/строки в возрастающем порядке. Порядок UI и запросов не влияет на результат.

1. По каждой строке отдельно распредели `line_total_minor` пропорционально `share_bp`. В предварительном расчёте добавь виртуальную долю `unassigned` с bp = 10000 − сумма реальных bp. Так сумма реальных частей и нераспределённого всегда равна строке.
2. Сложи доли строк по участнику: `B_u`; виртуальный остаток тоже учитывается. Не складывай сначала приблизительные проценты с float.
3. Распредели общую скидку `D` методом остатков пропорционально `B_u`: `D_u`. `A_u = B_u − D_u`.
4. Распредели чаевые `T` методом остатков по `A_u`. Если сумма `A_u=0`, но `S>0`, используй `B_u`. Если `S=0`, не разрешать старт сборов: чек должен содержать положительные позиции.
5. `due_u = A_u + T_u`. Всегда `sum(due_u including unassigned) = G`. Если реальный участник имеет `B_u=0`, он не получает чаевые при стандартной политике.
6. В `collecting` долги предварительные. `unassigned` не представляет человека и не записывается как долг создателя. В `settling` он равен нулю и отсутствует в финальном snapshot.

Создатель видит `own_cost` и `expected_from_others = G − own_cost`. Участник видит своё `due_minor` и расшифровку скидки/чаевых. Не использовать округлённые промежуточные цифры из UI для расчёта на сервере.

### Обязательные эталоны

| Данные | Результат |
| --- | --- |
| 1000 ₽; создатель 40%, участник 60%; скидка 10%, чаевые 10% от 900 ₽ | Итог 990 ₽; создатель 396 ₽, участник 594 ₽ |
| Строка 100,01 ₽; доли 50%/50%; без доплат | 50,01 ₽ участнику с меньшим UUID, 50,00 ₽ другому |
| Строка 100 ₽; 33,33% + 33,33% + 33,34% | 33,33 ₽; 33,33 ₽; 33,34 ₽ |
| 1000 ₽; доля пользователя 25%, остаток 75%; скидка 100 ₽; чаевые 90 ₽ | Предварительно 247,50 ₽ пользователю, 742,50 ₽ нераспределено |
| 1000 ₽; 40%/60%; скидка 100%; фиксированные чаевые 100 ₽ | Основной долг 0; чаевые 40 ₽/60 ₽ |
| Тот же чек, скидка 100%, чаевые 10% | Итог 0 ₽; закрытие всё равно требует явной кнопки создателя |

## Этап D. Ревизии и подтверждения выбора

- `receipt.version` — для optimistic concurrency всех команд чека.
- `financial_revision` меняется при правке суммы, количества, позиции, скидки/чаевых, участника или долей. Название чека без изменения расчёта увеличивает только `version`.
- Участник подтверждает выбор для текущей financial revision. Любое финансовое изменение аннулирует все подтверждения выбора; UI сообщает об этом. Это простой безопасный MVP, даже если иногда требует повторной кнопки.
- Snapshot в `settling` хранит строки, доли, скидку, чаевые, финальные долги и financial revision. Не рассчитывать уведомление по живому состоянию, отличному от snapshot.
- Два конкурентных изменения долей: блокировка строки чека в транзакции → проверка expected version → проверка total bp → изменение → version/revision++. Один проигравший получает 409 и актуальное состояние.

## Этап E. Реальные деньги и редактирование после переводов

- Отметка «Перевёл» — заявление участника об отправке конкретной суммы для snapshot, статус `reported`. Она не меняет подтверждённый баланс.
- Только создатель фиксирует `received` и сумму фактически полученного перевода. Можно подтвердить часть и затем остаток. Ввести по умолчанию текущий остаток, но разрешить фактическую сумму в пределах лимитов.
- Реально полученные средства хранятся в `cash_ledger`: положительный приход, отдельно подтверждённый возврат. Записи неизменяемы, исправление — компенсирующая запись с причиной. Участник не пишет ledger.
- `verified_net_u = received_u − refunded_u`; `remaining_u = due_u − verified_net_u`. Отрицательный remaining = требуется возврат, а не «всё оплачено».
- Создатель может вернуть `settling → collecting` с предупреждением и причиной. Полученные деньги сохраняются; snapshot становится историческим, незавершённые заявления по нему — `superseded`; долги пересчитываются, подтверждения выбора сбрасываются.
- Изменение цены с 500 ₽ до 400 ₽ после получения 500 ₽ даёт переплату 100 ₽. Закрытие блокируется, пока создатель не подтвердит возврат 100 ₽. Повышение до 600 ₽ даёт остаток 100 ₽.
- Удаление позиции очищает её доли, увеличивает revision, показывает, кого затронуло. Исторический snapshot сохраняет старую строку. Нельзя удалять участника, у которого есть подтверждённые деньги, заявления или доли: сначала урегулировать расчёт; в MVP участников с ledger оставлять в составе до закрытия.
- Отзыв прав доступа бывшего участника не стирает денежную историю. Проектируй удаление pending-участников отдельно от удаления accepted.
- Никакой автоматической выплаты/возврата приложение не выполняет.

## Этап F. Условия сборов и закрытия

Переход к `settling`: чек содержит позиции; OCR-кандидаты проверены создателем; позиции полностью распределены; все accepted-участники подтвердили текущую revision; нет unresolved/pending приглашений (создатель отменяет лишние); параметры валидны. В snapshot включены все accepted, включая нулевые долги.

Переход к `closed` в одной транзакции:

1. Запрос от создателя и корректная expected version.
2. Статус `settling`; snapshot актуален.
3. Для каждого accepted-участника кроме создателя `verified_net_u == due_u` точно в копейках. Нулевой долг не требует фальшивого перевода.
4. Нет неподтверждённых заявлений: создатель подтверждает, отклоняет или отмечает дубликатом все reported. Нет переплат, остатков и нерешённых возвратов.
5. Создатель отдельной кнопкой подтверждает полное получение; записать `closed_at = now_utc`, `purge_at = closed_at + 7 days`.

Повторный close с тем же idempotency key возвращает прежний результат и не сдвигает purge_at. Закрытый чек не редактируется и не открывается повторно в MVP.

## Этап G. Проверка инвариантов

Обязательны property-based тесты денег, проверка переходов и интеграционные конкурентные тесты в настоящем PostgreSQL. Специально проверять 0%, 100%, 100% скидку, нулевой долг, минимальные копейки, перебор долей, переплату, правку после получения, повтор close, purge на границе времени.
