# Авторизация и защита

## Этап A. Telegram identity

Mini App отправляет сырой `Telegram.WebApp.initData` только в POST body на `/auth/telegram` по HTTPS. Сервер проверяет HMAC по актуальной официальной спецификации Telegram; не доверяет `initDataUnsafe`, `user.id` из JSON клиента или URL.

- secret_key = HMAC-SHA256(key=`WebAppData`, message=bot_token).
- data-check-string строится по текущим правилам Telegram из декодированных полей, в алфавитном порядке и с LF. Для bot-token/HMAC метода исключается `hash`; не смешивать его с отдельной Ed25519 схемой, где правила отличаются. Проверить актуальную спецификацию для поля `signature` и добавить fixture.
- constant-time сравнение hash; валидный Telegram user обязателен.
- `auth_date`: по умолчанию возраст ≤10 минут, допустимое опережение часов ≤30 секунд; clock UTC. Эти сроки — политика нашего приложения, а не требование Telegram.
- Отказ при повреждённой кодировке, дублирующихся критических параметрах, невалидном JSON, отсутствии hash/user/auth_date.
- Bot identity берётся только из проверенного Telegram Update; webhook проверяется secret header. Long polling — отдельный dev-профиль, не одновременно с webhook.

После успешной проверки — opaque server session: случайный токен, в БД digest, cookie Secure+HttpOnly+SameSite=Lax, срок 12 часов, same-origin Mini App/API. Не использовать localStorage для bearer token. При долгой работе истёкшая сессия требует повторного входа/переоткрытия Telegram, свежесть initData не отключать ради удобства. Replay initData в его коротком окне не считать автоматически устранённым; ограничивать auth rate, не логировать данные.

## Этап B. CSRF и dev-режим

Для cookie-auth mutation проверять Origin и CSRF-токен; CORS — точный allowlist, credentials, никаких `*`. Если транспорт в конкретном Telegram клиенте не поддерживает выбранную cookie-схему, воспроизвести на устройстве и оформить явное ADR для безопасной альтернативы.

Dev login разрешён только при `APP_ENV=development`, `DEV_AUTH_ENABLED=true`, локальном origin и отдельном маршруте. В production процесс должен отказать старту при включённом dev auth. Playwright использует тестовые подписанные initData либо изолированный dev-профиль. Нельзя тестовый Telegram ID отправлять как production identity.

## Этап C. Права и приглашения

- Каждый запрос проверяет receipt membership; asset/job/item/report/member должны принадлежать тому же чеку.
- Создатель не может подменять Telegram identity участника. Он может принять заявку и добавить известного пользователя из собственных ранее принятых контактов приложения.
- Адресное приглашение для известного Telegram ID принимается только этим ID; новое принятие не создаёт дубликат membership.
- Для человека без известного ID: создатель делится request-only ссылкой, человек авторизуется и подаёт заявку, создатель её принимает. До приёма позиции/фото/полный список участников недоступны.
- Токен приглашения: минимум 128 бит криптографической случайности, digest в БД, TTL по умолчанию 72 часа, отзыв создателем, проверка статуса и срока. URL/startapp не является подтверждением личности.
- Обычная ссылка на уже доступный чек не добавляет участника и не обходит ACL.
- Контакты приложения ограничены отношениями с текущим пользователем. Не раскрывать всю users таблицу и не обещать поиск любого @username через Bot API.

## Этап D. Защита файлов и вычислений

Проверять фактический формат декодером, MIME и размер; JPEG/PNG/WebP, HEIC только при установленном проверенном декодере. Telegram document скачивается по server-side file_id, не по произвольному URL из запроса. Отдельные лимиты размеров, пикселей, страниц, jobs/user; защита decompression bombs; private random storage keys; EXIF удаляется. Сканы PDF вне MVP.

OCR выполняется с timeout, ограничением памяти и worker concurrency. Пользовательский текст чека не является инструкцией агенту или программе. Если VLM включён, возвращает только валидируемые данные по schema, без tools, без доступа к secrets, без выполнения «инструкций» с картинки.

Rate limits: auth, invite resolve, join, mutation, upload/OCR. В нескольких API replicas лимитер должен быть общим или ограничение реализуется reverse proxy; in-memory нельзя выдавать за глобальный. Идемпотентность: одинаковые actor+scope+key и body → прежний ответ, другой body с тем же key → 409.

## Этап E. Секреты и приватность

`.env.example` содержит имена и placeholders; bot token/ключи не в git и frontend bundle. Логи не содержат raw initData, cookie, приглашения, OCR-текст, банковские данные, фото или полный Telegram profile. Записывать request_id, тип операции, технический error code. Audit финансов — только в защищённой БД и удаляется вместе с чеком.

Все accepted участники видят распределение и статусы своих общих чеков; персональные контакты и сессии чужих пользователей недоступны. Экран приватности объясняет обработку фото, 7-дневный срок закрытых чеков и ограничения хранения внешних Telegram сообщений/резервных копий. Внешний OCR provider отключён по умолчанию и не отправляет чеки без отдельно выбранной пользователем настройки.
