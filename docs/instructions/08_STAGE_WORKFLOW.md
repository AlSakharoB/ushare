# Выполнение этапов, проверка, отчёты и коммиты

Этот файл обязателен после каждого этапа S00–S11, включая этапы с заблокированной внешней проверкой.

## Этап A. Перед началом

1. Прочитай `00_README.md`, спецификации по теме, текущее задание и существующий AGENTS.md.
2. Выполни `git status --short`, узнай branch/HEAD. Не стирай и не включай чужие незакоммиченные изменения. При пересечении выясни безопасный способ продолжить; для новых независимых файлов работай дальше.
3. Прочитай последний `reports/PROGRESS.md` и отчёты зависимостей. Отметь точный этап и scope.
4. Запиши короткий план: работа, проверки, ожидаемые артефакты. Уточняй только противоречия, которые действительно меняют результат; используй допущения этого комплекта для обычных решений.
5. Для этапа после блокировки прочитай реальную причину и не выдавай старый отчёт за актуальный.

## Этап B. Реализация

- Выполняй цель полностью; не заменяй backend заглушками, UI муляжом или OCR моками в рабочем профиле.
- Меняй минимально достаточный набор файлов; миграции, config.example и документация входят в этап, когда нужны для воспроизведения.
- Добавляй meaningful тесты изменённого поведения. Ручной smoke допустим как дополнение; для денег/ACL/гонок/retention требуются автоматические тесты.
- Проверяй ошибки и отключённые зависимости. Не «лечи» сбой ослаблением авторизации или отменой constraints.
- Не пушить, не сливать ветки, не создавать теги, не подключать платные сервисы и не публиковать production без отдельного поручения. Локальные атомарные коммиты этапов прямо разрешены этим заданием.

## Этап C. Проверка перед коммитом

1. Прогони необходимые для этапа команды. Запиши точную команду, exit code, число тестов, краткий вывод, elapsed при performance проверке.
2. Проверь миграции/контракты при их изменении; frontend typecheck/build при изменении UI/API types.
3. `git diff --check`, обзор `git diff`, `git status --short`; проверь случайные secrets, приватные fixtures, временные файлы, model weights, дампы, .env.
4. Проверь каждый acceptance item. «Код написан» ≠ «работает». Моковая проверка transport ≠ live Telegram smoke. Synthetic OCR ≠ реальные чеки.
5. Если провал: исправь и повтори относящиеся проверки. Если невозможно — точный `BLOCKED`, причина, что необходимо, какие независимые шаги продолжены. Не ставь DONE при обязательном провале.

## Этап D. Формат отчёта

Файл `reports/stages/Sxx_<short-name>.md`:

```markdown
# Sxx — Название
Дата UTC: ...
Статус: DONE | BLOCKED | IN_PROGRESS
Базовый HEAD: ...

## Результат
Что теперь умеет пользователь/система, 2–5 конкретных пунктов.

## Изменения
Основные файлы/модули и назначение; миграции/конфигурация.

## Проверки
| Команда / сценарий | Результат PASS/FAIL/NOT_RUN | Доказательство |
| --- | --- | --- |
| ... | ... | exit code, число тестов, ссылка на артефакт |

## Критерии приёмки
| ID / критерий из задания | Выполнен | Доказательство |
| --- | --- | --- |

## Риски и блокировки
Только реальные ограничения. Если нет — «Нет выявленных блокировок».

## Решения
Допущения, ADR, актуальные versions/model revisions, отклонения с причиной.

## Коммит
Planned subject: feat(scope): ...
Коммит этапа содержит этот отчёт. Его точный SHA выводится пользователю
после создания и доступен через git log по указанному subject.
Не добавлять самоссылочный SHA в содержимое собственного коммита.

## Продолжение
Следующий этап, оставшиеся gates, команды запуска/состояние.
```

Обнови `reports/PROGRESS.md`: таблица этапов с status, report path, commit subject; pending gates. Точный SHA предыдущего этапа можно записать на следующем этапе. Не коммить шумные огромные логи: безопасные сокращённые доказательства в отчёте, полные логи — gitignored artifacts/.

## Этап E. Локальный коммит

- Убедись в repository identity; если git не инициализирован — инициализируй локальный repo. Не выдумывай author name/email и не меняй global git config; отсутствие identity — блокировка коммита, работа/отчёт сохраняются.
- Один завершённый этап обычно один commit; при большом объёме допустимы логические атомарные промежуточные коммиты, итоговый отчёт охватывает весь этап.
- Conventional Commits: `chore(project): scaffold services and checks`, `feat(auth): validate Telegram sessions`, `feat(money): calculate exact receipt shares`, `feat(ocr): recognize and review receipt items`, `fix(retention): purge expired receipts and assets`.
- Добавляй конкретные относящиеся к этапу paths, не бездумное `git add .` в чужом рабочем дереве.
- Не переписывай чужую историю. Не использовать reset --hard, force push, rebase чужих изменений.
- Отчёт и PROGRESS входят в тот же commit. После commit — `git log -1 --format='%h %s'`, `git status --short`; проверь, что intended staged files вошли.
- При BLOCKED допустим отдельный commit уже проверенной независимой части с точной пометкой в отчёте. Он не переводит этап в DONE. Если commit недоступен, выводи «коммит не создан» и причину.

## Этап F. Сообщение пользователю

После этапа коротко: результат; проверки PASS и что не запускалось; commit SHA/subject или блокировка; следующий этап. При поручении всего проекта продолжай, не ожидая формального «продолжай». При поручении одного этапа остановись после отчёта/коммита. При нехватке внешних ресурсов задай один конкретный вопрос и параллельно продолжи независимую работу.

## Этап G. Возобновление

Новый запуск читает PROGRESS, последний отчёт, git status/log и реальный код. Выполненное не переписывать заново. Не считать галочку в документе доказательством при явном изменении кода. После исправления обновляй отчёт новой датой и новым коммитом; не редактируй историю ради «красивого» статуса.

## Стандартные команды проекта

На S00 создай Makefile с целями для уже существующих проверок; остальные добавляй на соответствующем этапе. Не делать пустые цели, которые всегда возвращают success. README должен объяснять prerequisite/env каждой команды.

| Команда | Что реально проверяет | Когда обязательна |
| --- | --- | --- |
| `make check-backend` | ruff + typecheck + unit tests | Изменения backend |
| `make check-frontend` | lint + tsc + unit + production build | Изменения frontend/DTO |
| `make test-integration` | PostgreSQL integration, ACL, transactions/races | Изменения БД/доменного API |
| `make test-e2e` | Playwright против реального test backend | S07 и изменения сквозного поведения |
| `make migrate` | Alembic upgrade head | Новая схема/чистый запуск |
| `make benchmark-ocr` | Real dataset, выбранные профили, JSON/MD metrics | S09 и изменение OCR profile/parser |
| `make smoke` | Compose services, health и основной сценарий | S00/S11 и изменения infra |
| `make check` | Доступная общая регрессия без скрытых skips | Финальная приёмка |

Full OCR benchmark остаётся отдельной командой: без dataset `make check` не должен утверждать, что качество OCR проверено. Команды выполнения backend/frontend можно реализовать через uv/npm/другой согласованный runner; отчёт сохраняет реальные invocation и exit codes.
